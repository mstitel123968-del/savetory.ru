ИНСТРУКЦИЯ ПО НАСТРОЙКЕ И ЗАПУСКУ Хранилище (savetory) (Django)
===============================================

Документ описывает два сценария запуска сайта Trezo: локально и в Docker.
Фронтенд (HTML/CSS/JS) перенесён без изменений, поэтому все стили и функции
должны работать так же, как в исходной версии.

1. Предварительные требования
-----------------------------
* Git.
* Python 3.11+ (для локального запуска).
* PostgreSQL 15 (или совместимая версия).
* Docker Desktop / Docker Engine c Docker Compose v2 (для контейнерного запуска).
* Библиотеки для Pillow (libjpeg, zlib). Они требуются при сборке образа и при
  локальной установке зависимостей. В Docker они уже ставятся автоматически.

2. Получение исходников
-----------------------
```bash
git clone <адрес-репозитория>
cd Mysite_v.1
```

3. Переменные окружения
-----------------------
Приложение читает параметры из переменных окружения. Для локального запуска
удобно создать файл `.env` со значениями по умолчанию:
```env
DJANGO_SECRET_KEY=замените-на-случайное-значение
DJANGO_DEBUG=1
DJANGO_ALLOWED_HOSTS=localhost 127.0.0.1 [::1]
POSTGRES_DB=trezo
POSTGRES_USER=trezo
POSTGRES_PASSWORD=trezo
POSTGRES_HOST=localhost
POSTGRES_PORT=5432
```
Файл можно загрузить командой `export $(cat .env | xargs)` в macOS/Linux или
с помощью `set` в PowerShell. На Windows обязательно укажите `POSTGRES_HOST=localhost`.

4. Локальный запуск (без Docker)
--------------------------------
1. Создайте виртуальное окружение:
   ```bash
   python -m venv .venv
   source .venv/bin/activate          # Windows: .venv\Scripts\activate
   ```
2. Установите зависимости:
   ```bash
   pip install --upgrade pip
   pip install -r requirements.txt
   ```
3. Выполните миграции и при необходимости создайте администратора:
   ```bash
   python manage.py migrate
   python manage.py createsuperuser    # по желанию
   ```
4. Соберите статические файлы для продакшн-режима (не обязательно для runserver):
   ```bash
   python manage.py collectstatic
   ```
5. Запустите сервер разработчика:
   ```bash
   python manage.py runserver
   ```
6. Откройте http://127.0.0.1:8000/ и проверьте, что фронтенд отображается корректно.

5. Запуск через Docker (рекомендуется)
-------------------------------------
Docker окружение повторяет продакшн-настройку: статические файлы собираются
автоматически, обслуживаются через WhiteNoise, а база данных запускается в
отдельном контейнере PostgreSQL.

### 5.1 Подготовка
* Убедитесь, что Docker и Docker Compose v2 установлены.
* При необходимости создайте `.env.docker` со своими значениями и подключите его
  в `docker-compose.yml` (поле `env_file`). По умолчанию в compose уже заданы
  переменные для локального запуска с БД внутри Docker.

### 5.2 Сборка и запуск контейнеров
```bash
docker compose up --build -d
```
Команда выполнит следующие шаги:
* соберёт образ `web`, установит Python-зависимости и запустит `python manage.py collectstatic --noinput`;
  если сборка статических файлов завершится с ошибкой, сборка прервётся;
* запустит контейнеры `web` (Django + Gunicorn + WhiteNoise) и `db` (PostgreSQL 15).
  Стартовый скрипт перед запуском Gunicorn дождётся доступности базы данных, поэтому
  в логах можно увидеть сообщение вида «Waiting for PostgreSQL ...». Это нормальное
  поведение: как только Postgres поднимется, приложение продолжит загрузку.
* после успешного подключения к Postgres автоматически применит миграции (`python manage.py migrate --noinput`),
  а затем принудительно пересоберёт статику (`python manage.py collectstatic --noinput --clear`), чтобы
  файлы из контейнера всегда соответствовали текущему коду.

Проверьте журналы, чтобы убедиться, что статика собрана и контейнеры стартовали:
```bash
docker compose logs -f web
docker compose logs -f db
```

### 5.3 Применение миграций и создание администратора
После того как контейнеры запущены, миграции уже применены автоматически. При необходимости
повторить процедуру вручную (например, после добавления новой миграции) выполните:
```bash
docker compose exec web python manage.py migrate
```
По желанию создайте администратора:
```bash
docker compose exec web python manage.py createsuperuser
```

### 5.4 Дополнительные команды
* При необходимости повторной сборки статики (например, если вы монтируете проект внутрь контейнера во
  время разработки) выполните:
  ```bash
  docker compose exec web python manage.py collectstatic --noinput
  ```
* Проверка наличия собранной статики (для диагностики проблем с отображением стилей):
  ```bash
  docker compose exec web ls staticfiles
  ```
  В каталоге должны появиться подпапки `css`, `js`, `images` и т.д. Если каталог пустой,
  повторите `collectstatic` и убедитесь, что команда завершилась без ошибок.
* Просмотр работающего сайта: http://localhost:8000/

### 5.5 Остановка контейнеров
```bash
docker compose down
```
Для очистки данных БД выполните `docker compose down -v` (удаляет volume `postgres-data`).

### 5.6 Советы по разработке
* По умолчанию каталоги проекта не монтируются в контейнер `web`, чтобы не потерять
  собранную статику. Если нужно разрабатывать с горячими правками, добавьте монтирование
  `.:/app` и установите `DJANGO_DEBUG=1`, затем пересоберите образ. Не забудьте повторно
  запустить `collectstatic` перед возвращением к продакшн-настройке.
* Если меняете переменные окружения, пересоберите образ командой
  `docker compose up --build`.

6. Работа с медиа-файлами
-------------------------
* Пользовательские изображения сохраняются в каталоге `media/`.
* В Docker каталоги `media` и `postgres-data` находятся внутри контейнера. Для резервного
  копирования используйте `docker compose exec web tar czf /tmp/media.tgz media` и затем
  `docker cp`.
* В продакшн-среде рекомендуется настроить отдачу медиа через Nginx или CDN.

7. Диагностика типовых проблем
------------------------------
* **Нет стилей после запуска в Docker.** Проверьте, что сборка не завершилась ошибкой
  на этапе `collectstatic`. Убедитесь, что вы не монтируете локальную папку поверх `/app`,
  иначе статические файлы из образа будут скрыты. Повторите `docker compose exec web python manage.py collectstatic --noinput`.
* **Django жалуется на ALLOWED_HOSTS.** Добавьте нужные адреса в переменную окружения
  `DJANGO_ALLOWED_HOSTS` (через пробел). По умолчанию разрешены `localhost`, `127.0.0.1` и `[::1]`.
* **Ошибки Pillow.** На локальной машине установите системные библиотеки libjpeg и zlib,
  затем повторите установку зависимостей. В Docker всё уже собрано.

Следуя указанным шагам, вы получите полностью работающее Django-приложение Trezo с
оригинальными стилями и JavaScript-функциональностью как при локальном запуске, так и в Docker.
